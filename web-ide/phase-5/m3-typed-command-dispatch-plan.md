# Phase 5 M3 Plan: Typed Command Dispatch and Runtime Dispatcher Wiring

## Objective
Deliver a deterministic command dispatch path where typed commands can be invoked from UI, executed in CL runtime, and returned as structured `command.result` or `command.error` messages.

## Scope
### In Scope
- `command.invoke`, `command.result`, and `command.error` payload contracts.
- UI runtime command client and correlation with command history.
- WASM runner transport wiring for inbound command requests.
- CL runtime dispatcher wiring for a first command set.
- Automated acceptance tests for round-trip command dispatch.

### Out of Scope
- Restart metadata enrichment beyond M3 contracts (M4).
- Inspector place-edit mutation protocol beyond command dispatch skeleton (M5).
- Background job scheduler protocol (M6).

## Baseline and Constraints
1. Runtime bridge envelope v1 and `runtime.output` flow are complete (M1/M2).
2. Typed command model v0 is stable and already used by UI.
3. CL currently emits JSON but does not have a general-purpose JSON parser.
4. M3 must avoid introducing brittle parser complexity into Lisp runtime.

## M3 Decisions (Locked)
1. Add bridge kind `command.invoke` for UI to runtime requests.
2. UI performs DWIM argument defaulting and sends a materialized invocation.
3. Runtime returns exactly one terminal response per invocation: `command.result` or `command.error`.
4. For WASM transport, canonical JSON payload is adapted into a binary command frame that Lisp can decode without JSON parsing.
5. Runtime response events continue to use `KERNEL_OP_RUNTIME_EVENT`.

## Contract Definitions
### Envelope
All M3 messages use runtime bridge envelope v1:
- `version`, `kind`, `jobId`, `streamId`, `requestId`, `seq`, `ts`, `payload`, `error`

`requestId` is mandatory for `command.invoke`, `command.result`, and `command.error`.

## `command.invoke` Payload (Canonical)
```json
{
  "invocation": {
    "id": "inv-000123",
    "commandId": "runtime.eval.form",
    "args": { "form": "(+ 1 2)" },
    "defaults": { "package": { "source": "selection" } },
    "source": "palette",
    "ts": 1738992004000
  },
  "context": {
    "package": "CL-USER",
    "selection": { "kind": "presentation", "id": "pres-44" },
    "sourceLocation": { "file": "foo.lisp", "line": 42, "column": 7 }
  },
  "dispatch": {
    "mode": "async",
    "timeoutMs": 30000,
    "idempotencyKey": "inv-000123"
  }
}
```

### Invariants
- `invocation.id` must be stable and unique per workspace session.
- `invocation.commandId` must be namespaced.
- `invocation.args` and `invocation.defaults` must be JSON-serializable.
- Runtime must treat duplicate `idempotencyKey` as idempotent within a bounded replay window.

## `command.result` Payload
```json
{
  "invocationId": "inv-000123",
  "commandId": "runtime.eval.form",
  "result": {
    "valueSummary": "3",
    "presentationId": "pres-91"
  },
  "effects": {
    "output": { "kind": "recording.rerun", "recordingId": "rec-77" }
  },
  "diagnostics": [],
  "durationMs": 4
}
```

### Invariants
- `invocationId` must match the originating `command.invoke`.
- `result` must be JSON-serializable.
- `effects` is optional and follows `web-ui/src/command-effects.mjs` output contract.

## `command.error` Payload
```json
{
  "invocationId": "inv-000123",
  "commandId": "runtime.eval.form",
  "phase": "execute",
  "retryable": true,
  "condition": {
    "type": "simple-error",
    "summary": "Undefined function FOO",
    "presentationId": "pres-err-1"
  },
  "diagnostics": []
}
```

### Invariants
- Exactly one terminal response for each invoke: result or error.
- Error payloads must preserve actionable condition summary.

## Transport Adaptation (WASM Runner)
### Problem
Canonical payloads are JSON, but Lisp has no current JSON parser.

### Strategy
Use a host-side adapter that translates `command.invoke` JSON to a compact binary frame consumed by runtime poll APIs.

### New Kernel Opcode
- `KERNEL_OP_RUNTIME_COMMAND_POLL = 0x00000024`

### Payload
```
offset  size  field
0x00    u32   max_bytes
0x04    u32   flags (bit0=allow_pending)
```

### Response
Binary command frame:
```
offset  size  field
0x00    u32   frame_version (1)
0x04    u32   invocation_id_len
0x08    u32   command_id_len
0x0c    u32   args_form_len
0x10    u32   context_form_len
0x14    u32   reserved
0x18    ...   invocation_id_utf8
...            command_id_utf8
...            args_form_utf8
...            context_form_utf8
```

`args_form_utf8` and `context_form_utf8` are Lisp-readable forms, generated by host adapter from canonical JSON.

## Runtime Dispatcher Architecture
### Components
1. UI command client:
- Materializes typed invocation.
- Emits `command.invoke`.
- Tracks pending invocation promises keyed by `requestId`.

2. Host runtime transport adapter:
- Browser-hosted runtime: enqueue command frame for `KERNEL_OP_RUNTIME_COMMAND_POLL`.
- Remote runtime: send canonical JSON unchanged over websocket/postMessage.

3. CL runtime dispatcher:
- Polls command inbox at safe points.
- Decodes frame to invocation fields.
- Resolves command handler and executes.
- Emits terminal event via `KERNEL_OP_RUNTIME_EVENT`.

4. UI inbound handler:
- Applies `command.result` and `command.error`.
- Updates command history with runtime result and diagnostics.
- Applies `effects` via existing command-effect bridge.

## Runtime Command Registry (M3 Initial Set)
1. `runtime.eval.form`
2. `runtime.recording.rerun`
3. `runtime.restart.invoke`
4. `runtime.inspect.presentation`

All additional command IDs are deferred until M4/M5.

## Failure and Recovery Rules
1. Transport timeout:
- UI marks invocation failed with `phase=transport`, `retryable=true`.
2. Unknown command id:
- Runtime emits `command.error` with `phase=dispatch`, `retryable=false`.
3. Handler exception:
- Runtime emits `command.error` with condition summary and optional restart hints.
4. Duplicate terminal response:
- UI ignores duplicate after first terminal event and logs diagnostic.

## Observability
1. Per-invocation trace fields:
- `requestId`, `invocationId`, `commandId`, `dispatchTs`, `terminalTs`, `durationMs`
2. Debug stream:
- `runtime.log` events for queue overflow, decode failures, and unknown handlers.

## Risks and Mitigations
1. Risk: Lisp-side command frame decode drift.
- Mitigation: fixed frame version and strict decode tests in JS and C.
2. Risk: duplicate or missing terminal responses.
- Mitigation: explicit terminal state machine in UI client with timeout fallback.
3. Risk: command queue starvation.
- Mitigation: bounded queue, nonblocking poll, and safe-point pump cadence.
