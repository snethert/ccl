# Scale, startup and module granularity

Status: measurement plan, not executed evidence. This records the product risks raised in the user's supplied Claude feedback after the bounded logical-frame proof. The existing cons-only fixtures establish mechanisms at their recorded bounds. They do not establish production pause times, generated-loop safepoint latency, image startup time or per-Worker memory use.

## Correct the startup cost model

Restoring the heap requires its code manifest and the installer's dependency closure. The current design already permits lazy installation; it does not require installing every function in every Worker before the first Lisp expression. Each Worker needs its own instances and callable table entries, but compiled modules can be shared with Workers. Compare compiling once and distributing modules with compiling from bytes in each Worker; measure the actual implementation instead of multiplying an assumed full compilation cost by the Worker count. The blocked-Worker lazy path still needs the existing accessible-byte/stable-mailbox protocol; startup module delivery does not replace it. [WebAssembly.Module documentation](https://developer.mozilla.org/en-US/docs/WebAssembly/Reference/JavaScript_interface/Module)

The statement that browsers retain only HTTP-cached Wasm bytes is too broad. V8's current compilation-pipeline documentation describes cached optimized machine code for streaming compilation, with thresholds and different treatment of baseline code. This does not promise cache hits for every engine, small module, generated byte buffer or later browser session. Treat an HTTP-byte hit and a compiled-code hit as different observations, and retain engine evidence for the latter. [V8 compilation pipeline](https://v8.dev/docs/wasm-compilation-pipeline)

Module granularity changes more than table-call overhead. V8's June 2025 account of indirect-call inlining describes a same-instance restriction, making calls across instances a different optimization case. This is an engine-specific reason to test granularity alongside the ABI, not a portable guarantee of current optimization behavior. [V8 indirect-call optimization](https://v8.dev/blog/wasm-speculative-optimizations)

## Product measurements as generated code becomes available

The [B engineering choice](abi-choice.md) defers the hand-built C/C4/B comparison. Prioritize a generated B slice, then measure the startup, memory and GC behavior of useful code. The earlier synthetic counts (1,000/10,000/50,000 definitions and batches of 1/16/128/1,024) remain possible exploratory points, not a required matrix or U1 census result. Let concrete product questions and qualified census data determine which configurations to measure; no ranking sweep blocks compiler implementation.

| Axis | Required distinction and observation |
| --- | --- |
| Startup milestone | Network/source availability, validation/compilation request, instantiation, table installation, heap reconstruction, first successful Lisp expression, first call of a cold function and later usable workload. Preserve both elapsed total and component timings; asynchronous overlap means component times cannot simply be summed. |
| Cache state | Fresh browser profile/process; warm HTTP bytes with compiled-code reuse absent or unknown; verified compiled-code reuse across browser restarts; same-process reuse reported separately. Record URL, response/cache headers, engine/version, profile identity, trace evidence and cache eviction. A fast second call is not proof of persistent code caching. |
| Module distribution | Compile once then share modules before Workers enter blocking Lisp execution; per-Worker compilation from stable bytes; eager core plus lazy remainder. Record module count, binary bytes, installed function count and dependency closure at each milestone. |
| Workers and memory | 1, 2, 4 and 8 Workers on the recorded Mac, subject to declared resources. Separate shared code/heap from per-Worker instances, tables, TLS, C/explicit stacks, metadata and staging buffers; report reserved/committed versus resident/peak bytes and late-Worker creation cost. Do not multiply shared allocations by Worker count. |
| Call path and tier | Same-module direct call, same-instance indirect call and cross-instance indirect call; monomorphic and changing targets; baseline versus warmed optimized execution. Preserve redefinition, generic fallback, tail transfer and observable outputs. Record native disassembly or engine traces where needed to identify elimination/inlining; do not infer dispatch cost from source syntax. |
| GC and safepoints | Vary live heap and root counts, allocation pressure, poll spacing and Worker count. Separate request-to-last-park latency, collector work and release-to-progress latency. Measure actual emitted loops; distinguish hand-built loops from later compiler-generated loops. Stop and retain resource exhaustion or timeouts instead of increasing limits to obtain PASS. |

B is selected for simplicity, independently of a measured ranking or a fixed production packaging. Stage 1 determines module granularity and eager/lazy installation while confirming generated-code correctness. Record those assumptions when measuring product behavior. Reopen the ABI only for a concrete problem; a future comparison must demonstrate sensitivity and account for packaging, engine tier and representative call distribution.

## Product budgets and evidence

No startup or memory budget has yet been approved, and no production-sized measurement exists. Record product targets for first usable expression, delayed-call latency, supported devices and resident memory before calling the result acceptable. The optional future comparison parameters in `benchmarks.json` are retained; its dedicated-host fixture deadlines do not become browser product promises. Do not invent absolute acceptance thresholds from a favorable exploratory run.

Retain the generator or generated-code revision, call-graph/manifest hashes, every profile binary, browser/engine flags, individual trials, cold-cache setup and raw traces in the evidence repository. Node results can test the fixture and characterize Node; they cannot substitute for browser startup evidence. Missing browser features, trace access or a target budget remain explicit gaps. No result in this plan changes the existing acceptance inventory by itself.
