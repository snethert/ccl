# Exploratory ABI measurements and prebuilt-code publication

Run from the repository root on the macOS reference host:

```sh
node --liftoff-only --no-wasm-tier-up --no-wasm-lazy-compilation tests/wasm/stage0/abi-measurements/run.mjs --output /absolute/path/to/new-empty-evidence-directory
```

The default is three independent paired trials, 100 ms warmup and 50 ms sampling per workload. These are exploratory settings, below the unchanged selection policy. To exercise that policy's duration and trial minima, pass `--trials 30 --warmup-ms 1000 --sample-ms 250`. Neither mode selects an ABI: representative workloads, remaining correctness/engine prerequisites, independent review, product budgets and several resource metrics remain open. The runner rejects extra or missing engine flags. Its Node/V8 identity, executable tool hashes and V8 option listing are retained. All three packaging choices and all three candidates are mandatory in this runner.

The runner first executes the unchanged dynamic-call corpus and its frame/runtime/boundary prerequisites. It then builds an isolated derivative with a new C observation helper linked to the same boundary/kernel objects. The original dynamic-call, frame and integrated-runtime sources are unchanged. The derivative's six starting files are explicit copies of the reviewed build, actor, harness, function emitter, support emitter and schema; shared correctness cases are imported from the reviewed corpus. This makes the source delta visible without patching the reviewed fixture at runtime.

Each candidate and packaging combination runs 54 correctness cases, 31 rejection controls, eight batch checks and three batch controls. That is 486 positive cases, 279 rejected controls, 72 positive batches and 27 rejected batch controls, in addition to fresh prerequisites. Changed code requires its own independent review. The measurement bodies, support, dispatcher and published entries have the same bytes during qualification and timing; a runtime mode disables diagnostic packet construction and forwarding inside timing.

## Call paths and timed work

The eight hand-built function definitions can live in one bundle, or in eight separate instances. The same-module direct configuration puts the dispatcher and all callees in one module and uses direct tail-call instructions. The same-instance configuration dispatches through the table to that bundle's entries. The cross-instance configuration dispatches to separately instantiated callable modules. Unknown-callee workloads use indirect dispatch in every configuration; nested and cross-arity tail calls also retain table dispatch. All callable entries are eagerly installed before measurement. Bundled configurations retain the individual callable bytes for identity validation but instantiate the bundle; resource reports distinguish these bytes.

A timed export loops in Wasm over a retained, seeded 32-record input schedule. Warm and sample batches traverse whole schedules, keeping the declared subcase mixture identical across candidates. Host clocks surround the batch, and all host reporting and assertions occur afterwards. Admission/parking at batch boundaries, argument staging, frame/root publication, bindings, cleanup, result ownership, graph consumption, polls and runtime schedule counters remain charged. Tail binding checks remain charged as well. The runtime's schedule import is a Wasm counter/forwarding shim: diagnostic mode forwards to the host; measured mode counts without forwarding. A host request or callback inside a timed batch fails the run.

The eight workloads cover arity boundaries, changing indirect targets, distinct closure environments, optional/rest/keyword mixtures, rooted APPLY list construction, zero/one/six values and nested preservation with GC, 2,000-transfer cross-arity chains, and allocation with forced moving collection. Each batch consumes the first-value/count pair and every result word through an address-independent graph traversal, including sharing and cycles. An independent JavaScript model supplies the expected observation. The 32-bit rolling observation is a correctness checksum, not a collision-free equivalence proof. Batch controls discard observations, duplicate a result scanner and reuse a moved self; the normal semantic/state/collector checks reject them.

The three original review observations have concrete follow-ups. `measure_ownership` checks physical scanner addresses and advertised result counts at legal inspection points, outside the no-poll handoffs. The private Worker table has a code/role/function registry: publication validates all slots before filling any, and a control substitutes an actual same-signature function before checking the registry. The timed lookup is Wasm; the host checks the private table before a batch, and no table mutation is permitted during it. Circular APPLY is accurately named as reaching the fixed argument-capacity condition; no cycle-detection algorithm is claimed.

## S0-LL21-a

Worker 0 validates prebuilt code/version bytes, writes their identity to a shared publication record and releases a generation word. An already existing Worker and a later Worker each acquire that generation, validate the digest, encounter their own uninstalled entry, install matching roles and execute the new version. The first Worker can still call the old function object. Missing publication and a corrupted digest are rejected; the late Worker also collects during installation. This is an explicitly identified new execution, not a relabeling of the accepted LL21-b evidence.

## Evidence and limits

Fresh output retains inputs, sources, WAT, binaries/objects, toolchain and engine flags, protocol/semantic traces, every mutant and failure, the matrix frozen before timing, individual first/warm/sample batches, startup component timings, resource observations and paired bootstrap calculations. Bootstrap resampling preserves all candidates and eight workloads within a trial; inner iterations are not independent trials. The statistics checker exercises known ratios, common trial drift, missing/duplicate/invalid input and insufficient trials/durations. The standalone S0-LL21-a v2 envelope stays NOT_REVIEWED; the 24 measurement IDs remain exploratory and cannot provide S0-ABI-selection.

Bounds remain explicit: eight hand-built definitions, 32 arguments, six values, 512-byte frames, a 16 KiB explicit and C stack reservation per ownership slot, four ownership slots, two live measurement Workers (three in publication correctness), one shared 1 MiB linear memory and two 4 KiB semispaces. Graph observation admits at most 64 cons nodes per value; batches admit at most 4,096 iterations. Capacity or protocol failures terminate the run. This is not an arbitrary-size workload, a generated CCL backend or a production image startup measurement.

Resource records distinguish executable/module and metadata bytes, adapters/stubs, table slots, shared reservations and per-slot reservations, observed explicit-stack/root high-water marks, compilation/instantiation and first-batch latency. Startup refers to fresh Worker isolates within an existing Node process; it does not establish browser cache state or image reconstruction. `rss` is process-wide; Worker heap reports are not resident-per-Worker measurements. Dynamic root-store/reload counts, peak C-stack use, engine code bytes, safepoint/GC phase latencies and resident Worker memory are explicitly unavailable. Debug policy 1 still materializes roots and changes reporting only; the actual storage is charged. No product acceptance thresholds have been invented.
